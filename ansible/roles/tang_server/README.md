# tang_server

Runs [Tang](https://github.com/latchset/tang) on the Raspberry Pi in the
`rasp_servers` group, for network-bound disk unlock of the homeserver
(Clevis). Tracker #41.

Applied by its own playbook, never by `site.yml`:

```bash
.venv/bin/ansible-playbook ansible/playbooks/rasp.yml --ask-become-pass
```

On the first run skip `--check`: the package and its units don't exist
yet, so a dry run fails on them.

- Tang listens on port 80 (Debian's `tangd.socket`) over plain HTTP, which
  is how the protocol is designed: it never receives the disk key.
- **LAN only, one client.** `iptables` accepts port 80 from
  `tang_server_allowed_ipv4_clients` (the homeserver's inventory address)
  and drops it from everyone else, over IPv4 and IPv6. Never forward this
  port: a Tang reachable from outside lets a stolen machine unlock itself.
- Keys live in `/var/lib/tang`, generated by `tangd` on first request.
  **They are deliberately not backed up.** If the Pi or its SD card dies,
  unlock with the LUKS passphrase, set up a new Tang and rebind the
  disks. A copy of the keys elsewhere would only widen what a thief can
  use.
- Security updates come from `unattended_upgrades`, with Raspbian's own
  origins set in `group_vars/rasp_servers`. No automatic reboots.

Check that the firewall holds. From the homeserver this prints the
advertisement, from any other LAN device it times out:

```bash
curl --max-time 5 http://192.168.178.110/adv
```
